### ANSWERS

1. **Sidecar ownership** – The only component capable of writing `sidecar.json` today is a *future* Scout daemon. In the current repo, no writer exists; the bus (`whorl_bus`) could be used to serialize side‑car updates from any privileged skill (e.g., `governor` after an Oracle approval). If multiple writers race, the bus’s logical clock and `acknowledge()` can serialize writes, but the spec must declare a *single* authority (e.g., `governor → sidecar`) and treat the side‑car as *tentative* until the Oracle signs off. “Ground truth” is therefore a *derived* state, not absolute, especially when P5 may replace it.

2. **Priority hierarchy correctness** – A cache‑first order (P1 → P2) is unsafe when the cache can be poisoned. The safer ordering is **P2 (verification) before P1**, i.e., *validate* the side‑car against the current environment (via `oracle.audit_text` or a cheap RAG check) and only fall back to the cached copy if verification succeeds. This prevents blind trust in stale or malicious data.

3. **Vote weighting** – The four channels (`audit_log`, `reasoning_stream`, `native_consensus`, `adversarial_veto`) should be mapped onto the existing `arena_gladiator` scoring system rather than kept as independent opaque streams. Each channel becomes a “player” with an assigned weight (e.g., Oracle = 2, native = 1, reasoning = 1, veto = 3). `arena_gladiator` can then compute a weighted ELO outcome. If `adversarial_veto` (high weight) disagrees with a unanimous native consensus, the veto wins because its weight overrides the others; the system should still log the conflict for audit.

4. **What replaces the fictional roster** – Redefine §3 by **capability class**, not model name:  
   * **Audit** – any model that can call `oracle.audit_text` (e.g., `ox` with a “skeptic” persona).  
   * **Contradiction** – models that produce counter‑arguments (e.g., `aider` in dry‑run mode).  
   * **Synthesis** – the “native consensus” engine, which could be `ox`‑adapter or `puter` running a merge script.  
   * **Veto** – a privileged “Meta” channel that is simply the `governor` with a `--force‑veto` flag.  
   This removes the nonexistent names and ties the pipeline to the actual binaries present.

5. **Sequencing** – The logical first step is **“Test: mock daemon/scout.py”** *and* implement a side‑car writer (e.g., `scout/write_sidecar()`). Only after a concrete side‑car exists can you “Mold: integrate feed consumption in `inference_bridge`”. The “Zero‑tool‑call hydration” milestone should be moved **ahead of** “Mold” because hydration is the source of the side‑car data that `inference_bridge` will consume. A corrected order:  
   1. Mock/implement side‑car production.  
   2. Zero‑tool‑call hydration (populate side‑car on session start).  
   3. Wire `inference_bridge` to consume the bus.  
   4. Hook native simulation engines.  
   5. Automate multi‑model feedback weighting.
